# Zoho Catalyst AppSail: Development deployment

This deploys only the existing CredX backend. It does not create a Catalyst project,
deploy the frontend, promote to Production, or change application architecture.
This is a disposable Development deployment, **not production-ready storage**.

## Fixed target

| Setting | Value |
| --- | --- |
| GitHub repository / deployment branch | `Adhivp/CredX` / `main` |
| Catalyst project | `credx` / `54564000000101001` |
| Organization | `60077360744` |
| Environment | `Development` / record ID `54564000000101018` |
| Data center | `in` |
| AppSail name | `credx-api` |
| HTTP port | `9000` |

The project domain is not the AppSail URL. The helper obtains the actual AppSail
URL from Catalyst and prints only allowlisted service metadata.

The root `.catalystrc` and `catalyst.json` were produced by the official CLI's
`project:use` and `appsail:add` workflows. They contain no credentials.
`.catalystrc` intentionally stores `60077360744` as its environment `id`: CLI
1.29.1 maps the API's `env_zgid` to that field and uses it as the `CATALYST-ORG`
header. Do not replace it with the environment record ID. The helper verifies
both identifiers against the remote environment before any configuration write.

## Runtime and build

The Dockerfile pins `python:3.14-slim` to its verified image digest, with hash-checked wheels from the existing
`requirements.txt`, `/app`, UID/GID 10001, and a writable private `/app/data`.
The Python version remains `>=3.14,<3.15`. No declared dependencies were changed.
The first image import failed with `ModuleNotFoundError: pandas`; the fetched
main branch's lockfile and pip exports were stale relative to its existing EWS
dependencies in `pyproject.toml`. The three generated dependency artifacts were
regenerated with `uv lock` and `uv export`, retaining existing resolved versions.

Build from the repository root:

```sh
docker buildx build --platform linux/amd64 --provenance=false --load \
  -f backend/Dockerfile -t "credx-api:$(git rev-parse HEAD)" .
python3 backend/scripts/smoke_container.py "credx-api:$(git rev-parse HEAD)"
mkdir -p .catalyst-artifacts
docker save -o .catalyst-artifacts/credx-api.tar "credx-api:$(git rev-parse HEAD)"
```

The root context is necessary because EWS routes import `core.rules` and
`core.models`. The image carries `core/__init__.py`, `core/rules`, the model code
`core/models/*.py` and the trained models `core/models/saved/*.joblib` (cash-flow
and warning-score; without them scoring falls back to the rule composite). The
tracked `backend/data/credx.db` is copied to `/app/seed/credx.db` as a **seed**.
The frontend, raw datasets, training logs, dotenv files, caches, and credentials are
excluded. A root `.dockerignore` allowlists these runtime inputs; do not build with
`backend/` as the context.

Startup is a shell CMD:

```sh
umask 077; python -m app.db.bootstrap && python -m alembic upgrade head && exec python -m uvicorn app.main:create_app --factory --host 0.0.0.0 --port 9000
```

`app.db.bootstrap` never deletes data. If `DATABASE_URL` points at a missing or empty
file, it copies the seed there with user accounts and login sessions removed (the seed
is in a public repository; register a new account after each fresh deployment).
If the database was built by `create_all` and has no `alembic_version` table, it
stamps revision `0001` so the upgrade does not fail on existing tables. Override the
seed location with `DB_SEED_PATH`.

`&&` prevents Uvicorn starting after a failed migration. `exec` gives Uvicorn PID 1
and SIGTERM. The Docker healthcheck uses `/health`. No secret is a Docker ARG,
Docker ENV instruction, image label, or artifact. The smoke test supplies its
own random, disposable signing key and checks HTTP, migration head, a fresh empty
users table, non-root execution, shared-rule imports, repeat migration, and
clean SIGTERM shutdown. No test requests mutate the remote application's data.

Review Python base-image security updates regularly. To update its digest, inspect
`docker buildx imagetools inspect python:3.14-slim`, update the Dockerfile in a PR,
and repeat the AMD64 build, migration, HTTP and shutdown tests before merging.
Do not move to a different Python series without application compatibility review.

## GitHub settings

Create repository Actions secrets (not variables):

- `CATALYST_TOKEN`: token generated by the official Catalyst CLI for the India
  account with access to this existing project and AppSail Read/Create/Update.
- `JWT_SECRET`: stable cryptographically random value, minimum 48 characters.
  Do not regenerate it for each deployment; rotation invalidates existing JWTs.

The workflow defaults missing or empty target variables to the existing India
Development project below. These IDs and region are public configuration, not
secrets. You may also set repository Actions variables explicitly:

```sh
gh variable set CATALYST_PROJECT_ID --repo Adhivp/CredX --body 54564000000101001
gh variable set CATALYST_ORG_ID --repo Adhivp/CredX --body 60077360744
gh variable set CATALYST_ENVIRONMENT --repo Adhivp/CredX --body Development
gh variable set CATALYST_DC --repo Adhivp/CredX --body in
```

If preflight reports `Refusing deployment: incorrect CATALYST_PROJECT_ID` (or
another target key), inspect **Settings > Secrets and variables > Actions >
Variables**, not the Secrets tab. An unset `vars.KEY` expands to an empty string;
the workflow now supplies the fixed Development default in that case. A nonempty
incorrect value is still rejected: correct it to the exact value above, with no
quotes or whitespace. Do not remove the target guard or use a Production value.
Environment-scoped variables are not available unless the job selects that GitHub
environment; use repository variables here. `CATALYST_TOKEN` and `JWT_SECRET`
remain required secrets and have no defaults. After a workflow change reaches
`main`, start a new manual run; rerunning an old failed run uses its old revision.

CLI authentication procedure (in a trusted terminal, never in CI logs/chat):

```sh
npm install --global zcatalyst-cli@1.29.1
catalyst login --dc in
catalyst token:generate --dc in
# Enter the generated CLI token in GitHub > Settings > Secrets and variables > Actions.
# Alternatively, gh secret set CATALYST_TOKEN --repo Adhivp/CredX prompts privately.
```

`catalyst token:generate --current --dc in` can retrieve the existing signed-in
CLI credential. Treat its output as a secret. The CLI accepts `CATALYST_TOKEN`
in the process environment (also `ZC_TOKEN`), so the workflow never supplies the
token on a command line. This is a Catalyst CLI token, not a raw OAuth access
token to be placed in an Authorization header. The pinned CLI manages refresh.
Use a trusted maintained Node release: the workflow pins patched Node 24.22.1.
The preinstalled Node 22.23.3 emitted a CLI security warning and was not used for
the successful remote deployment.

The first live Development deployment generated a separate random signing key,
stored only at `/data/workspace/credx-deployment/jwt-secret` on the setup machine
(mode 0600, outside Git). Once GitHub authentication is available, preserve that
key when creating the repository secret:

```sh
gh secret set JWT_SECRET --repo Adhivp/CredX < /data/workspace/credx-deployment/jwt-secret
```

For a different setup machine, securely transfer that key through your secret
manager, or deliberately rotate the Development key. Never commit the file.

## Workflow behavior

`.github/workflows/deploy-catalyst.yml` runs for backend changes on `main` and
manual `workflow_dispatch`. Relevant shared rules, workflow, Docker and Catalyst
configuration changes also trigger it. PRs to main build and smoke-test without
secrets and **cannot deploy**. Manual runs on another branch only build/test.

1. Read-only checkout with persisted Git credentials disabled; actions pinned to
   immutable commits and CLI pinned to the inspected version.
2. Deployment-helper contract tests, then Docker Buildx builds `linux/amd64` and
   tags the image with the GitHub SHA. The Docker exporter produces an archive.
3. Load and exercise the actual image, including Alembic and HTTP endpoints.
4. Pass the tested archive to the deployment job as a one-day GitHub artifact.
   No public registry or Docker registry credentials are needed.
5. Validate all target variables and secrets, install the official CLI, and inspect
   the existing project/Development environment and service identity remotely.
   Deployment selects the project explicitly through `--project` and `--org`; CI
   does not run the local RC-mutating `project:use` command.
6. `catalyst deploy appsail --name credx-api --source docker-archive://... --port 9000`
   upserts by name. It creates a missing service or updates the existing one;
   `appsail:add` only links local configuration, it is not a remote create command.
7. Wait for asynchronous image creation to finish, apply application environment
   variables via AppSail configuration, and verify them in memory by reading back.
8. Fetch actual service details from Catalyst; poll `/health`, then require 200
   from `/docs` and `/openapi.json`. Login redirects fail validation. Publish
   the service URL in the job summary, without credentials.

Deployments from main are serialized; in-progress deployments are not cancelled.
A failed build, smoke test, target guard, upload success check, configuration
read-back, or HTTP probe fails the workflow. CLI 1.29.1 can return exit zero when
individual targets fail, so its explicit deployment-success marker is also checked.
This is deployment CI, not a claim that the entire existing application suite is green.

### CLI limitations and the configuration companion

The inspected CLI has no `--environment`, `--env-vars`, `appsail:create`,
`appsail:logs`, or scaling min/max flags. `deploy` targets Development.
Do not invent those flags or use a production promotion command.

In 1.29.1, Docker deployment ignores `env_variables`; `app-config.json` is for
managed runtimes and is not read for Docker images. The regular custom-target
path also forces Catalyst authentication on. The workflow therefore uses the
official standalone Docker deploy command and a small companion script:

- `backend/scripts/catalyst.cjs` uses the authentication and API transport shipped
  in **exactly** `zcatalyst-cli@1.29.1` to call the same configuration endpoint
  implemented by its `AppSail.updateConfig` method:
  `POST /baas/v1/project/{project}/appsail/{service}/configuration` with
  `environment.variables`. It also sets port 9000 and requests Catalyst auth off;
  the application retains its own JWT auth. Public route probes verify no login
  interception, even when the API omits the auth flag in its response.
- Existing unrelated environment keys (including an optional Nebius key) are
  preserved. No secret configuration JSON is written into the repository.
- It waits for image creation to complete **before** applying environment values.
  A real first-deploy attempt showed early configuration being overwritten when
  the asynchronous deployment finalized. A read-back immediately after an early
  write alone was not sufficient.
- API transport instances are single-use: the CLI mutates URL/body state. Reuse
  would send requests to the wrong path. A regression test covers isolation.
- The redaction option in CLI 1.29.1 also disables its HTTP-error rejection.
  The companion independently rejects every missing/noninteger/non-2xx status;
  error bodies and credentials remain suppressed. Regression tests cover a failed
  configuration POST even when existing values would match the intended write.
- These internal module interfaces are not a stable public SDK. Reinspect and
  retest the companion before changing the CLI version. The supported console
  fallback is AppSail > credx-api > Configuration > Environmental Variables.

### CLI 1.29.1 CI-mode project association

`project:use` fails in GitHub Actions with `.catalystrc file needed to upsert
project` even when the tracked file exists. The CLI
`command_needs/rc.js` returns early in CI after setting project/org IDs, without
loading an RC object; `project:use` then calls `upsertProject`, which requires one.
Creating another RC file does not fix that control flow. Do not disable CI mode
or create another project to work around it.

The workflow instead verifies the existing remote Development environment using
`node backend/scripts/catalyst.cjs inspect` and retains explicit `--project`,
`--org`, and `--dc` options on the official CLI deploy command. The tracked
`.catalystrc` remains available for local CLI use. Do not use `CI=false`: the CLI
treats any nonempty CI value as true.

## Manual Development deployment and validation

After building/exporting above, run from the repository root with a securely
provided JWT_SECRET and either CLI login or CATALYST_TOKEN in the environment:

```sh
export CATALYST_PROJECT_ID=54564000000101001
export CATALYST_ORG_ID=60077360744
export CATALYST_ENVIRONMENT=Development
export CATALYST_DC=in
export NODE_PATH="$(npm root --global)"

node backend/scripts/catalyst.cjs inspect
catalyst deploy appsail --name credx-api \
  --source docker-archive://.catalyst-artifacts/credx-api.tar --port 9000 \
  --project "$CATALYST_PROJECT_ID" --org "$CATALYST_ORG_ID" --dc in --non-interactive
node backend/scripts/catalyst.cjs configure
node backend/scripts/catalyst.cjs verify
```

After merging the reviewed PR yourself, run:

```sh
gh workflow run deploy-catalyst.yml --repo Adhivp/CredX --ref main
gh run list --repo Adhivp/CredX --workflow deploy-catalyst.yml
```

The workflow is not registered for manual dispatch until it is on the default
branch. This change does not merge its PR or push to main.

### Logs and migrations

Inspect Catalyst Console (India), existing credx project, **Development**:

- AppSail > credx-api > Deployments: confirm successful image deployment.
- Instances > History > selected instance's logs icon: opens DevOps execution logs.
- Confirm Uvicorn listens on `0.0.0.0:9000`; look for migration/startup errors.

The official console docs state deployment logs are available only for images
fetched directly from container registries, **not CLI-uploaded Docker archives**.
There is no established CLI command to download these remote runtime logs. CI
prints CLI deployment output and local-container runtime logs; remote console
runtime-log review remains a manual check. Do not call those remote logs checked
merely because HTTP probes pass.

Locally the smoke test reads SQLite's `alembic_version` and compares it to the
migration script heads; it also runs `alembic current` and repeat `upgrade head`.
Remotely a successful new-image startup implies the CMD's migration gate passed,
but `/health` is process liveness, not a database integrity or durability check.
The current auth migration is `0001`. EWS tables are created by the existing
application factory's `Base.metadata.create_all`, not Alembic migrations. This
behavior is preserved, not endorsed as a production schema management strategy.

### SQLite and existing application safety limitations

- AppSail documentation describes instance-local disk allocation, cold starts,
  replacement and automatic scale-down, but establishes no durable SQLite volume
  contract. Treat `/app/data` as disposable. A new instance starts from the seed
  (the `credx.db` committed at build time), so it is never empty; uploads, users and
  sessions created after that are lost on a replacement, scale-down or redeployment.
  To keep data, commit an updated `backend/data/credx.db` and redeploy, or move to a
  durable database.
- One Uvicorn worker does **not** mean one AppSail instance. AppSail can create
  multiple isolated instances; their SQLite files diverge. No supported single-
  instance control was established, and this workflow does not invent one.
- No backup/restore automation, persistent storage, encryption-at-rest guarantee,
  or database durability has been established. Even limiting instances would not
  solve restart durability. A durable shared database requires a separately
  reviewed application change: `configure_database` currently rejects non-SQLite.
- Use synthetic, disposable data only. Obtain written storage/lifecycle guidance
  from Catalyst support before relying on this for anything valuable.
- Cold starts include migrations; the documented listen deadline is 10 seconds
  and request timeout is 30 seconds. Revisit this strategy for larger migrations.
- Existing main hardcodes wildcard CORS with credentials and ignores configured
  `CORS_ORIGINS`. EWS routes also require an independent authorization/security
  review. This deployment does not fix or rewrite that application logic.
- The API schema/reference is now regenerated and its documentation tests pass.
  The full application suite still has migration/model drift and unlisted-origin
  CORS failures, plus a garbage-collection-dependent unclosed-SQLite-connection
  warning attributed to varying security test cases. These application issues
  remain separate from this CI/docs fix; do not describe this as a green full-suite
  release.

There is no automatic database rollback. Redeploying an older image is not a safe
rollback for incompatible migrations or a substitute for restoring backups.
